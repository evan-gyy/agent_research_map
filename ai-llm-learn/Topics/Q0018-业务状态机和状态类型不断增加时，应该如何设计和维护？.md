# 业务状态机和状态类型不断增加时，应该如何设计和维护？

## 原题原文

> 如果业务中的状态机数量不断增加，状态类型扩展到二十多种甚至更多，应该如何设计和维护？

## 答案

### 面试直答

业务状态不断增加时，应把状态机从散落的 if/else 中抽离：定义有限状态、合法事件、转移守卫和副作用，使用版本化 Schema 和集中 Reducer；状态爆炸时用分层/并行状态机，而不是继续增加组合枚举。

### 一、模型

```text
State + Event --Guard--> NewState + Commands
```

状态只描述事实，命令负责副作用；转移要幂等并记录事件。把“支付状态×任务状态×审核状态”拆成正交子状态，避免笛卡尔积。

> **核心小结：** 状态、事件、转移和副作用分离，才能控制复杂度。

### 二、治理

使用迁移表和契约测试覆盖合法/非法转移；持久化版本与幂等键；超时和补偿作为显式事件；增加新状态前检查是否其实是标签或派生属性。

> **核心小结：** 可维护状态机依赖集中规则、可回放事件和自动化转移测试。
