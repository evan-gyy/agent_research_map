# 如何验证 Agent 项目效果？最终评测结果如何？

## 原题原文

> 怎么验证项目效果，最终的评测效果怎么样？

## 答案

### 面试直答

验证 Agent 项目要同时看端到端结果和节点过程。基于当前 Dynamic Planner 仓库，我能确认 Planner、并行 Executor、Judge、Summary、内容校验和 SSE 的实现，但仓库没有一份可审计的最终线上指标报告，因此回答时不能编造“提升了多少”。正确做法是展示评测设计，并替换成自己真实跑出的数据。

### 一、怎么验证

- 建立旅行查询分层集：酒店、景点、多意图、约束冲突、多轮补充和工具失败。
- 为每题标注必需信息、可接受答案和标准工具证据。
- 节点层评估 Planner 子目标、工具成功/延迟、Judge 漏判和 Summary 忠实度。
- 端到端评估任务完成率、引用正确性、首屏/P95 延迟、成本和人工接管。
- 与固定 Workflow、单轮模型、顺序工具调用等基线做同数据对照。

> **核心小结：** 必须有同一数据、同一约束下的基线和分层指标，才能证明编排改动有效。

### 二、结果应该怎样表达

可以使用以下结构，但方括号必须替换成真实数据：

```text
在 [N] 条冻结测试集上，端到端任务成功率从 [A] 到 [B]；
P95 延迟从 [C] 到 [D]，平均工具调用从 [E] 到 [F]；
主要收益来自 [并行执行/检索改进/Judge]，主要失败仍是 [具体类型]。
```

同时报告样本量、置信区间、模型和工具版本。若多轮重试提高准确率，要单独报告一次直出、有限步和完整研究模式，不能把更多计算换来的结果包装成同延迟收益。

> **核心小结：** 好的项目结果包含收益、成本、样本量和剩余失败，而不是一个孤立准确率。

### 三、当前能诚实给出的结论

源码能够证明系统设计支持并行技能、有限充分性判断和流式返回；它不能单独证明线上效果。若被追问具体数字，应展示实际评测表或明确说明尚未完成量化，不用估算值代替。

> **核心小结：** 架构事实来自代码，效果事实来自冻结评测和线上数据，两者不能混用。

### 常见追问

- **Judge 会不会自评偏高？** 会，应使用人工标注集校准，并与规则或独立模型交叉验证。
- **为什么不能只看用户点赞？** 点赞稀疏且有选择偏差，需要结合任务成功、改写和人工接管。
