# 源码级 Agent 拆解交付标准

## 目标读者与表达

默认面向有工程背景、但没有读过目标源码的中文读者。先给直觉和全局图，再进入协议对象、调用链与源码；每个复杂章节末尾用一句“核心小结”收束。

## 推荐结构

1. 定位、版本与证据边界
2. 一页结论与模块地图
3. 端到端运行流程
4. 核心状态对象或协议
5. Agent Loop / Planning
6. Context 组装、截断、压缩与恢复
7. Tool 系统、Schema、执行与错误
8. Extension / Plugin / MCP
9. Permission、沙箱与副作用
10. Session、Resume、Fork 或持久化
11. Subagent / 并发（如果存在）
12. 可观测、测试与评估
13. 完整运行示例
14. 源码阅读路线
15. 可迁移经验、限制与待核验项
16. 来源

不存在的模块可以省略，但应明确“不支持”或“公开资料未发现”，不要留一个空章节。

对模块化 Agent 额外提供“默认内建 / 可扩展实现 / 有意不内建 / 实验中”能力表。这张表用于解释产品哲学与集成责任，不应用功能数量给产品简单排名。

## 图表标准

源码级深挖通常至少提供以下四种不同信息视图：

- **端到端流程图**：从用户输入到最终结果。
- **时序图或状态图**：展示模型、Runtime、Tool、Session 之间的事件顺序或状态变化。
- **模块/证据表**：职责、入口、状态与证据等级。
- **Context 或扩展机制图**：展示 Prompt 组成、Extension 加载或消息重建。

复杂产品可增加：错误分支图、目录树、权限决策图、数据对象关系图、并发 DAG。每张图后用正文解释“为什么这样设计”和“代价是什么”。图中名称必须能映射到真实符号；概念映射用虚线或文字说明。

不要用多张图重复同一条主链。流程图应回答控制流，表格应回答精确映射，状态图应回答变化与恢复。

## 代码与伪代码

至少包含：

- 一个核心循环或等价伪代码；
- 一个关键数据结构或接口；
- 一个工具/扩展注册例子；
- 一个用户可运行的最小示例；
- 一个失败或边界示例。

节选必须短、带路径/符号/Commit，并在节选后逐行解释关键决策。非公开快照只做小段架构说明，不大段复刻。

## 示例设计

完整示例应贯穿同一个任务，例如“读取项目并修复测试”或“搜索资料并生成报告”，逐步展示：

```text
用户输入
-> Context 初始构成
-> 模型第 1 次响应
-> Tool Call 与 Tool Result
-> Context 第 2 次构成
-> 最终响应
-> Session/日志落盘
```

再给至少一个失败变体：工具报错、参数非法、用户中断、Context 超限或 Extension 冲突。不要只给 Happy Path。

## 事实与推断标注

章节表格中使用证据标签；正文首次陈述关键机制时给源码或官方链接。以下句式有助于控制边界：

- “官方文档明确说明……”
- “提交 `<commit>` 的 `path#symbol` 可以确认……”
- “下面用 ReAct 作概念映射，产品并未使用这一正式命名……”
- “公开资料没有披露……，因此不推断……”
- “以下为工程建议，不代表目标产品现状……”

## 解释深度

每个核心模块回答五件事：

1. 它解决什么问题？
2. 输入、输出和持有的状态是什么？
3. 它在主调用链的哪个位置？
4. 失败时发生什么？
5. 为什么选择这种设计，代价是什么？

仅列文件名或类名不算解释。仅贴代码而不解释控制权也不算源码拆解。

## 最终质量检查

- 读者能否只看主图说出一轮如何运行？
- 图中每个核心节点是否有源码或官方证据？
- 是否区分产品当前事实、历史实现和教学类比？
- 是否展示了 Tool Result 如何回到下一轮？
- 是否展示了停止、异常、取消或恢复路径？
- 是否有完整示例和失败示例？
- 是否说明哪些常见能力目标产品没有？
- 是否记录 Commit、核验日期和无法验证的范围？
- 是否运行文档验证器和相关项目测试？

## 将真实使用反馈回写 Skill

用 Skill 完成一个新产品后，只把可跨产品复用的缺口回写：例如新增证据标签、发现通用的状态图要求、验证器漏检了源码导航。不要把某个产品的目录名、私有机制或偶然故障写成普遍规则。
