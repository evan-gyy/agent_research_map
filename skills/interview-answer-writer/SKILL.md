# 面试题答案写作

为正式题卡撰写可以直接用于面试表达、同时讲清原理与工程实践的中文参考答案。本项目默认题库为 `ai-llm-learn/Topics/`。

## 工作流程

1. 读取题卡的 `normalized_question`、`原题原文`、主题、来源与已有答案；只回答规范问题，不修改原题证据。
2. 判断题型和面试官真正考察的能力，再决定答案结构；不要机械套用相同章节、公式或图表。
3. 核验技术事实。涉及项目经历时读取实际项目的当前代码、说明与活跃调用链；事实不足时提供回答框架并明确需要补充的信息，不虚构经历、指标或线上效果。
4. 先写可在 20～40 秒内说完的“面试直答”，再用短段落和分点展开原理、流程、工程实践与取舍。
5. 在每个主要章节末尾用“核心小结”概括该节结论。
6. 只在显著提升理解时加入 Mermaid、表格、公式或伪代码；图示不能替代关键机制的文字解释。
7. 增加少量高价值常见追问；避免把答案扩写成百科全书。
8. 对抽象概念做一层“发散思考”：寻找一个真实业务场景和一个成熟公开 Agent/框架实例，解释它为什么这样选、怎么落地、付出什么代价。没有可靠证据时不强行举品牌案例。
9. 写入题卡的 `## 答案`，保持 `## 原题原文` 和 `## 问题来源` 不变，并把 `status` 从 `unanswered` 改为 `draft`。只有经过人工或明确复核后才改为 `reviewed`。
10. 校验 Markdown 结构、Mermaid 围栏、公式围栏、内部链接和答案状态；批量写作时先完成少量代表题并确认风格，再扩展到全库。

## 内容结构

按题目选择必要部分，不要求每题全部出现：

- `### 面试直答`：先给结论，不铺背景。
- `### 一、...`：解释定义、机制、输入输出或控制流程。
- `### 二、...`：说明关键步骤、组件关系、公式或图示。
- `### 三、工程实践与取舍`：覆盖落地方式、性能、成本、失败模式、适用边界。
- `### 常见追问`：通常 2～4 个高概率追问及简短答案。

主要章节应包含：

`> **核心小结：** 用一句话收束本节真正需要记住的结论。`

## 表达选择

- 概念题：定义 → 核心机制 → 与相近概念的边界 → 工程意义。
- 对比题：先给核心差异，再用对比表或控制流图说明选型条件。
- 模型原理题：直觉 → 必要公式或算法 → 复杂度或资源瓶颈 → 工程实现。
- 排障题：先定义可观测现象和指标，再沿链路分层定位，最后给单变量验证方法。
- 架构与开放设计题：约束 → 模块与数据流 → 可靠性和容量保护 → 取舍。
- 评估题：结果、过程、效率、可靠性和安全性 → 数据集 → 离线与线上闭环。
- 项目经历题：业务目标 → 当前真实主链路 → 关键工程设计 → 边界与代价 → 代码或文档依据。

## 业界实例与发散思考

- 概念讲清后，继续问：它在个人 Agent、低延迟业务 Agent、长任务 Agent 中分别怎么选？
- 示例应包含四项：**业务约束、实际机制、选择原因、局限或代价**；不要只写“某产品也用了”。
- 优先选公开且成熟的实例，例如 Codex、Claude Code；旅行 Agent 场景可使用 Dynamic Planner 的真实活跃链路。
- 将实例与概念对应时明确证据层级：
  - **官方文档或公开源码确认**：可以陈述具体机制，并附来源。
  - **概念映射**：可以写“可理解为”或“体现了类似思想”，不能说官方把它命名为该模式。
  - **经验性设计建议**：明确写成建议或参考实现，不冒充产品现状。
- 对 Codex/OpenAI 机制先查 OpenAI 官方文档；需要实现细节时再读 `openai/codex` 公开仓库并记录提交版本。
- 对 Claude Code 机制只使用 Anthropic 官方文档、官方 SDK 文档或官方公开仓库；公开资料没有披露的摘要 Prompt、服务端策略或指标不要猜测。
- 不强制每道题同时出现多个产品。只有实例能明显帮助理解或选型时才加入，避免答案被品牌介绍喧宾夺主。
- 可以在答案末尾加入“真实系统怎么做”或“延伸阅读与实现依据”，但题卡仍须独立回答原问题。

## 图、表和公式

- Mermaid 用于控制流、时序、模块依赖或离线/在线双链路；一张图只表达一个主要关系。
- 表格用于三个以上维度的对比、指标体系或明确映射。
- 公式仅在它能解释机制或定义指标时使用，例如 Attention、Softmax、复杂度、Recall@K、MRR 或训练目标。
- Workflow、Agent 架构和一般工程设计题通常优先使用流程图、表格和分点，不为形式统一而添加公式。
- 公式旁边必须用中文说明变量、直觉和工程意义；不能只列公式。
- 考虑部分 Markdown 预览器不渲染 LaTeX：即使公式显示为源码，周围文字也应能独立讲清结论。

## 写作约束

- 使用简洁、直白、专业的中文；避免长段连续文字和空泛套话。
- 不把“原理与工程”压缩成几句话，也不追求固定字数。内容以把问题讲清为止。
- 区分事实、经验建议和假设；没有唯一答案时使用“参考答案”，不声称“标准答案”。
- 不编造项目职责、生产数据、模型收益、用户反馈或公司内部信息。
- 相似题可以相互链接，但每张题卡必须能够独立复习和回答。
- 保留题卡的 `normalized_question`、`原题原文` 与来源证据；发现问题本身有缺陷时交给题库审计流程处理，不在答案里悄悄改题。

## 完成检查

- 面试直答是否先给出明确结论？
- 原理是否解释了“为什么”，工程部分是否说明了“怎么落地与有什么代价”？
- 图、表或公式是否确实提高理解，而不是装饰？
- 每个主要章节是否有清晰的核心小结？
- 是否在合适时给出了真实业务或成熟 Agent 实例，并解释约束、机制、原因和代价？
- 产品案例是否标明官方事实、源码事实或概念映射，是否附了可核验来源？
- 项目事实是否有当前仓库证据，是否区分活跃路径与旧代码？
- 原题原文、来源和规范问题是否保持未变？
- Mermaid 与公式围栏是否成对，`status` 是否正确？
